# Agent Mesh 代码审查请求（交给远程 AI 协作者）

> 用法：把本文件全文 + 仓库代码一起交给 AI（或告知 AI 本仓库地址让其读取）。

## 你的角色

你是本项目的远程 AI 协作开发者。请审查仓库当前代码，输出**问题清单与改进方案**。不要输出完整重写，只输出：分级问题清单（指出文件与函数）、每个问题的修改要点、新增功能的接口设计草案。

## 项目背景

- Go 双端 Monorepo：
  - `agent-mesh-server`：gin + SQLite 中央汇总中枢（心跳、设备拓扑、审计日志）
  - `agent-mesh-client`：libp2p P2P 节点 + MCP stdio 服务 + AI 工具适配器
- 定位：企业内网 AI 节点调度平台，数据不出内网
- 当前状态：双端 `go build ./...` 通过；Windows 真机联调通过（心跳 200、设备列表含真实内网 IP 与 agents 能力位、豆包适配器 Copy-on-Read 扫库并上报审计成功）

## 工程边界（审查与建议时必须遵守）

1. 心跳与审计交换严格遵循 `core/types.go` 的 `TaskPayload` 结构
2. MCP 协议 = 2024-11-05 + JSON-RPC 2.0，stdio 传输
3. 零侵入适配器：新增 AI 工具只能在 `adapters/` 实现 `AIAdapter` 接口后注册，禁止改主引擎
4. P2P 传输必须 libp2p 加密流 + SHA-256 尾部完整性校验
5. 监听第三方 SQLite 必须 Copy-on-Read 只读快照（防锁死官方客户端）
6. 依赖约束：SQLite 用 `modernc.org/sqlite`（纯 Go，无 cgo）；libp2p 锁 v0.33.2（0.34+ mDNS 移出主仓、Noise/Yamux 移出根包）

## 请重点审查（按优先级）

1. **中央→节点任务下发通道缺失**：现在只有心跳+审计上行，没有"服务端下发任务 → 节点执行 → 结果回传"的闭环。请设计最小任务下发协议（HTTP 轮询 vs P2P 直连，给出取舍与推荐），含消息 JSON 示例。
2. **P2P 无节点鉴权**：任何知道 multiaddr 的节点都能发起连接与传文件。请给出轻量方案（PSK / 节点身份白名单 / libp2p peer allowlist）。
3. **HTTP API 无鉴权**：`/api/v1/*` 在内网裸奔，任何内网主机可伪造心跳与审计。给出适合内网的最小鉴权方案（如共享密钥 header + 时间戳防重放）。
4. **mDNS 发现生命周期**：`mdnsNotifee` 的上下线清理是否有泄漏风险；Windows 下多网卡 multicast 的兼容性处理。
5. **MCP 工具集为空**：`RegisterTool` 机制已就绪但未注册具体工具。请列出应暴露给本地编辑器的最小工具集建议（如 `mesh.status` / `mesh.agents` / `mesh.sendfile`），含入参出参 schema。
6. **审计日志无留存策略**：SQLite 会无限膨胀，请给出滚动清理或按量截断方案。
7. 其他你发现的 bug、竞态、资源泄漏或不规范之处。

## 输出格式

- **P0（安全/崩溃）/ P1（功能缺口）/ P2（体验与规范）** 三级清单；每条包含：文件 + 函数 + 现状描述 + 修改建议
- 任务下发协议设计草案（消息结构 JSON + 状态机说明）
- 关键修改只给 diff 片段，不要整文件重写
- 最后给一个"建议的下一个里程碑"（一次迭代能落地的最小集合）
