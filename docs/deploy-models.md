# 交付形态与厂区内网方案（方案 B 改造）

> 2026-09-29 定稿。场景由"最坏情况（办公室之间完全不通）"收敛为**单厂区、多车间/办公室**，
> 并参照对标产品（汇智中枢）重新设计了方案 B。
> 关联文档：`docs/m3-lan-test-plan.md`（第 6 节）、`README.md`（安装段）。

---

## 0. 结论摘要

**同一厂区不同车间/办公室的互联可以实现，而且单厂区场景不需要公网 VPS。**

改造后的方案 B 从「on-prem 服务端 + **必配**公网 VPS 隧道」改为
「**厂区自持、按网络现实分三档**」：VPS 从"必须"降级为"仅跨厂区/厂外点可选"，
与对标产品的"无外部依赖"形态对齐。

向对标产品学三件事：

| 学什么 | 对标产品的做法 | 我们怎么落 |
|---|---|---|
| **独立性** | 闭源二进制，不依赖公网/第三方服务，客户自持整套 | VPS 变可选；单厂区零外部依赖 |
| **维护性** | 服务端、数据、升级都在客户内网，客户可控 | 服务端装厂区；审计数据不出厂区 |
| **售后少** | 前置条件写死 + 自助安装（邀请码 + 一行命令）+ 明确交付清单 | 出「网络接入要求一页纸」+ 自助安装 + 自检脚本 |

## 1. 为什么单厂区能实现互联（技术前提）

1. **控制面是 hub-spoke，只要各车间/办公室能 TCP 到服务端的内网 IP，就能接入。**
   厂区内部通常有自己的路由/交换设备，跨 VLAN 只要放行端口即可，不需要任何 overlay。
2. **唯一真正的障碍是 mDNS 不跨网段。**
   `agent-mesh-client/core/p2p_transfer.go:82` 只注册了 mDNS 组播发现，
   而组播只在同一广播域内传播 —— 跨 VLAN 时 P2P 文件传输会失效。修法很小（见 §3.3）。
3. **注意：文件传输目前只有 P2P 一条通道**（服务端没有文件中转接口，详见 §2.2 的更正）。
   因此"文件能不能跨车间传"完全取决于 P2P 能否恢复：
   - 同网段（L0）→ mDNS 可用
   - 跨网段但有路由（L1）→ 靠 §3.3 的服务端 peer 目录恢复
   - 跨 NAT（L2）→ P2P 无法恢复，需补**服务端中转（§3.5）**或上 overlay

## 2. 三档形态（按厂区网络现实选）

| 档 | 厂区网络现实 | 控制面 | P2P 文件传输 | 需要做什么 | 需要公网 VPS |
|---|---|---|---|---|---|
| **L0** | 所有车间/办公室同一网段（单交换机 / 单 VLAN） | 直连可用 | mDNS 直接可用 | 什么都不用 | 否 |
| **L1** | 多网段 / VLAN，厂区内有路由互通 | 路由可达即可 | mDNS 失效 → 需 §3.3 改造（peer 目录） | 放行端口 + 服务端 peer 目录（小改） | 否 |
| **L2** | 车间之间**无内部线路**，各自拉外网 | 需隧道（frp） | **P2P 不可达（跨 NAT）→ 需补服务端中转或 overlay** | frp 反向隧道（服务端在厂区，VPS 中继） | 是 |

**实施/售前判定入口（一句话）**：
> "你们厂区里，各车间、办公室之间现在能互相 ping 通吗？"

- 能，且在同一网段 → **L0**
- 能，但跨网段 → **L1**
- 不能 → **L2**

### 2.1 归属与责任边界（谁出 VPS、谁负责运维）

**要点：先"消掉需求"，再谈"归属"。** 改造的核心不是把 VPS 推给客户，而是
**让多数场景根本不需要 VPS**（L0 / L1）。只有 L2 才涉及一台公网机器，而那台机器的归属是商业选择。

| 档 | VPS 需求 | 谁提供 | 谁运维 | 我们交付什么 |
|---|---|---|---|---|
| **L0** | 无 | — | — | 零配置安装包 |
| **L1** | 无 | — | — | 「网络接入要求」一页纸 + peer 目录（代码） |
| **L2** | 一台有公网可达地址的机器 | **二选一，须在交付范围里写死** | 同左 | L2 配方（frp 配置模板 + 启动脚本 + 端口规划 + 验收清单） |

**更正（重要）**：本节初稿写过"文件经服务端中转是服务端本职"——**在当前代码里不成立**。
服务端**没有任何文件中转接口**，文件传输的唯一通道是 P2P。因此：

- **L1** 靠 §3.3 的 peer 目录把跨网段 P2P 恢复（对端地址在厂区内可路由）。
- **L2** 因跨 NAT，P2P 无法恢复 → 跨端传文件**要么补服务端中转（推荐，见 §2.2），要么上 overlay**。

真正"多出来的一台机器"只出现在 L2；但"跨端传文件"这个能力在 L1 / L2 都必须单独交代清楚。

**L2 的两种归属（必须二选一，不能含糊）**

- **客户自持（推荐，对齐"独立性 / 维护性 / 售后少"）**：客户用自己的云主机或公网服务器。
  我们只交付**可复制的配方**，不替他运维 —— 这条路我们不承担任何线上运维责任。
- **我们托管（= 原来那句"多出来的一个服务"）**：多客户共用一台 VPS，由我们运维。
  客户更省事，但**VPS 挂了会影响所有走 L2 的客户**，与"售后少"的目标相反，属商业取舍。

**更简的变体**：若客户接受审计数据出厂区，L2 可直接把**服务端放公网**（即方案 A 形态），
连 frp 都不需要；只有"数据必须留在厂区"才用 frp 隧道。

> **一句话总结**：L0 / L1 我们是"让客户不用想"；L2 我们是"给客户现成配方"，而不是
> "让客户自己想"。至于那台 VPS 谁出、谁运维 —— 那是商业条款，不是技术默认。

### 2.2 为什么 L2 用 frp，而不是 ZeroTier 等 overlay

**先交代：早期确实推荐过 ZeroTier。** 那是因为当时的场景是"家里 ↔ 办公室、且必须保住 mDNS P2P"。
场景收敛为"单厂区、L2 兜底"后，判定依据变了，结论随之反转。这不是前后矛盾，是**输入变了**。

| 维度 | ZeroTier / overlay 系 | frp 反向隧道 |
|---|---|---|
| 要装在哪 | 服务端 **+ 每一台客户端** 都装（含虚拟网卡驱动，Windows 需管理员权限） | **只有服务端侧一个 frpc**；客户端**零改动**，继续出站 HTTPS 到公网地址 |
| 要维护的控制面 | 官方 SaaS（境外、国内不稳，需代理）或自建控制器 + planet/moon（又是 VPS + 组件） | 一个开源单二进制 + 公网侧一个 frps 端口 |
| 二层广播 / mDNS | 支持（ZeroTier 是 L2）→ 跨网 P2P 可保 | 不支持 → 跨端文件直传需另行解决（见下） |
| 独立性 | 引入第三方组件与控制器依赖 | 客户自持一套，无第三方 |
| 售后面 | 多一层会坏、要跟上游升级的东西 | 活动部件最少 |

**更正一个此前写错的前提**：本节初稿写过"文件分发主路径是服务端中转、P2P 只是加速器"。
**当时这在代码里并不成立**（已核实）：服务端全部路由只有 9 个（心跳 / 设备 / 审计 / 任务），
**没有任何文件中转接口**；文件传输唯一通道是 P2P（`mesh.sendfile` → `core/p2p_transfer.go:208`），
对端不在 peerRegistry 时直接报错"未在局域网内发现或已离线"。
所以在那个时间点上，P2P 不通时跨端传文件是**不可用**，而不是"变慢"。

> **2026-09-29 更新**：服务端文件中转接口**已实现**（见 §3.5），上面那句"没有"已经过期。
> 现在跨端传文件不再依赖 P2P 可达性，"文件经服务端中转"从"待建前提"变成了"已具备的能力"。

**更正后的真实差别**：

| 能力 | frp 路线（L2） | ZeroTier 路线（L2） |
|---|---|---|
| 心跳 / 拓扑 / 任务下发 / 结果回传 / 审计（全经服务端） | 通 | 通 |
| 终端 ↔ 终端文件传输 | **通**（经服务端中转，§3.5 已实现） | 通（P2P 直传，不占用中枢磁盘） |

**结论随之修正**：

- 客户**只需要控制面**（任务 / 审计 / 统一管理）→ frp 足够，客户端零改动。
- 客户**需要跨端传文件** → 已由 §3.5 的**服务端文件中转**解决：文件先上传到厂区那台中枢，
  再由目标节点拉取。客户端零改动、不引入任何 overlay。**frp 路线成立的前提已经就位。**
- 只有这三种情况才值得改上 ZeroTier：客户**已在用** overlay / 明确要求跨车间
  **P2P 直传**（不接受经中枢中转）/ 未来接入机器数量很大且都归我们统一管理。
- 也就是说：**"用 frp 而不是 ZeroTier"这个选择，现在不再附带任何前提条件。**

另外，用 overlay 是在**扩大**要在客户现场落地的东西（每台机器一个虚拟网卡驱动 + 一个网络授权），
而 L2 客户的网络环境本就最糟、最需要"少活动部件"；frp 只多一个进程，且装在服务端那台机器上。

**什么时候仍应选 overlay（保留为 L2 的可选替代）**：
客户已在用 ZeroTier / 明确要求跨车间 P2P 直传且不接受经中枢中转 /
未来接入机器数量大且都归我们统一管理。
**除此以外，L2 默认用 frp —— 服务端文件中转（§3.5）已经补上，不再有前提条件。**

## 3. 改造后方案 B 的四个部件

### 3.1 服务端落地位置

- 厂区一台**常开**机器，固定内网 IP（静态地址或 DHCP 保留）：
  - 现有服务器 / 常开 Windows 办公机 → 用 `deploy/install-server.ps1`（已就绪）
  - Linux 小主机 / NAS / 群晖 → **需先补 Linux 安装脚本**（缺口，见 §5 步骤①）
- 建议装在网络最"中心"的位置（核心交换机机房 / 办公网），减少跨 VLAN 跳数。

### 3.2 给客户 IT 的「网络接入要求」一页纸（直接降低售后）

服务端监听端口：默认 `8443`（HTTPS）或 `8080`（HTTP）。

| 方向 | 端口 | 用途 | 必需性 |
|---|---|---|---|
| 客户端 → 服务端 | TCP `<服务端端口>`（如 8443） | 心跳、任务、审计上报 | 必须 |
| 客户端 ↔ 客户端 | TCP `6001`（`p2p_port`，可配） | P2P 文件直传 | 可选（**跨 NAT 时不可用**；需补服务端中转，见 §3.5） |

要点（写进交付材料，避免现场扯皮）：

- 只要求"能连到服务端 IP:端口"，**不要求任何 overlay / VPN**。
- 跨 VLAN 若被 ACL 拦，只需客户加一条"允许到服务端 IP:8443 / 6001"的规则。
- 服务端机器本身**不需要公网出口**（L0 / L1）。

### 3.3 跨网段 P2P：服务端 peer 目录（代码改造规格）

**现状（已核实）**

- `peerRegistry` 存 `peer.AddrInfo`（`core/p2p_transfer.go:52`），
  **唯一写入者是 mDNS 回调** `mdnsNotifee.HandlePeerFound`（`:377`）。
- 心跳只有 `client_id / client_name / os / ip_address / status / agents`（`api/device.go:15`），
  **缺 peer_id 与 p2p_port**。

**改造（约 100 行，不改现有协议语义）**

1. 把 `HandlePeerFound` 内的写入逻辑抽成公开方法 `RegisterPeer(peer.AddrInfo)`，
   mDNS 回调改为调用它（行为不变）。
2. 心跳请求加两个字段：`peer_id`（libp2p PeerID 字符串）、`p2p_port`（int）；
   写入 `devices` 表新增两列（沿用现有轻量迁移模式）。
3. `DeviceResponse` 带上这两个字段，`GET /api/v1/cluster/devices` 返回。
4. 客户端定时（建议 30s）拉取设备列表，为每个对端拼出
   `AddrInfo{ID: peer_id, Addrs: ["/ip4/<对端 ip_address>/tcp/<p2p_port>"]}` 并 `RegisterPeer`。
5. mDNS 路径保留（同网段零配置、最快）；服务端目录作为跨网段的补充。
   两条路径共用同一 registry，**`p2p_allow` 白名单与校验和机制完全不动**。

**边界与风险**

- 目录里的地址来自各节点**上报的自述 IP**，跨 NAT 不可用 → **仅适用于厂区内网（L1）**。
  L2 无法靠此恢复 P2P，需走 §3.5 的服务端文件中转（或 overlay）。
- `p2p_port == 0`（未启用 P2P）的节点不进目录。

### 3.4 自助交付：邀请码 + 一键安装 + 自检（学对标产品的售后模型）— **已实现**

> 完整设计、安全模型与排障表见 **`docs/enrollment.md`**；本节省略细节，只留结论。

对标产品的做法（已核）：后台签发**邀请码** → 员工打开邀请页 → 复制一行安装命令 → 自动装好。

已落地的能力：

1. 控制台加「签发邀请码」（可绑标签 / 有效期 / 可用次数），**一码一机**；明文只在签发时回显一次。
2. 邀请页给出一行命令
   （Windows：`irm <服务端>/join/<码> | iex`；Linux：`curl -fsSL <服务端>/join/<码> | sh`）。
3. 引导脚本极薄（只负责搬运），真正的安装逻辑在 Go 客户端 `enroll` 子命令里：
   用邀请码换 `playbook.json`（服务端地址、secret、`tls_ca_pem`）→ 落 CA → 装二进制 → 写 `agent-mesh.json` → 注册并启动服务。
4. 装完自动自检：权限、服务、端口、心跳连通性、控制台可见性 → 结果（分步明细）回传控制台。

实现要点（与初稿的差异）：

- **消费语义**：只有「取 `playbook.json`」才消费名额；落地页 / 脚本 / 客户端包 / 自检回传都不消费，
  `client_id` 幂等（同机重取不重复扣），自检回传在码已用尽时也放行（保证失败可见）。
- **安全**：只存 SHA-256 哈希（不落明文）；原子消费（`UPDATE ... WHERE` 判 `RowsAffected`）；
  `/join` 全组按连接 IP 限流 60 次/分且**不信任 `X-Forwarded-For`**；邀请码走 stdin 不落命令行/历史。
- **TOFU**：取包时客户端尚无服务端 CA，只能 `InsecureSkipVerify`；拿到 `tls_ca_pem` 后立即固定，
  后续通信严格校验。
- **权限前置检查**：先验权限再取包，避免"白烧邀请码后卡在注册服务"。
- **覆盖安装先停服务**：Windows 上运行中的 exe 被锁，必须先停再覆盖。
- **平台服务化**：Linux 补齐真实 systemd（`Restart=always`），消灭"关终端就断心跳"。
- 服务端新增 `-public-url`（反代/隧道下必填）与 `-client-pack`（客户端二进制目录）。

好处：**十几个人的公司不用你跑现场**，员工自己点一下完成；
把"售后工时"一次性换成"开发投入"，这正是对标产品售后少的原因。

**边界（说清楚不等于做到）**：邀请码**不是强席位控制**——它只负责"安全送密钥 + 留审计线索"，
鉴权仍靠集群共享 secret。按设备签发独立密钥是后续项（见 `docs/enrollment.md` §9）。

### 3.5 服务端文件中转接口（**已实现**）

**为什么需要**：文件原本只有 P2P 一条通道（见 §2.2 更正），跨 NAT（L2）时必然不通。
还有一个更实际的问题：**任务执行产出的文件取不回来** —— 结果字段只有一个文本
（`TaskResultReq.Result`），产物留在执行机本地，控制台看不到也下不了。

**设计**：文件不再依赖点对点可达性，改成「上传到中枢 → 目标节点拉取」。
中枢不解析文件内容，只做搬运与暂存。

| 接口 | 鉴权 | 说明 |
|---|---|---|
| `POST /api/v1/files/upload` | 专用 HMAC（用**实体摘要**签名） | 流式落盘，边收边算摘要 |
| `GET /api/v1/files?node=<id>[&pending=1]` | 常规 HMAC | 列出该节点可见的文件（定向给它的 + 广播的） |
| `GET /api/v1/files/download?file_id=&node=` | 常规 HMAC | 下载；定向文件只有目标节点能取 |
| `POST /api/v1/files/delete` | 常规 HMAC | 元数据与磁盘实体一并删除 |
| `GET /console/api/files`、`/console/api/files/download` | Basic Auth | 控制台总览与**直接取回**产出物 |

**客户端能力（新增）**

- `mesh.relayfile`：经中枢把本机文件送达指定节点（跨网段**唯一**可用的文件通道）。
- `mesh.fetchfile`：列出 / 领取中转给本机的文件。
- 常驻端每 20 秒自动领取**定向给自己**的文件并落盘；广播文件不自动落盘（避免污染所有机器磁盘）。
- `mesh.sendfile`（P2P）语义不变，失败时会提示改用 `mesh.relayfile`。

**四个关键取舍（都写进了代码注释）**

1. **上传鉴权不复用缓冲式中间件**。常规中间件为保证签名覆盖请求体内容，会先把整个 body
   读进内存再回填 —— 对几百 MB 的文件，那等于把"防篡改"做成了"自我 OOM"。
   改为客户端声明实体摘要、服务端据此重建同一套规范串：校验阶段内存占用是常数级，
   摘要与收到的字节是否相符，则由服务端边落盘边算兜底。**签名不覆盖实体这一缺口必须由它补上**，
   否则中间人可以不改签名就替换传输中的文件。
2. **落盘用随机 `file_id`，原始文件名只作展示**。于是路径穿越天然免疫，
   文件名仍做归一化后再进响应头（它是不可信输入）。
3. **可见性按节点过滤**。定向投递的文件不出现在其它节点的列表里，直接按 ID 下载也返回 403。
4. **领取是一次性的**。下载成功才标记，轮询不会反复拉同一个文件；中途失败保持未领取以便重试。

**限额与清理**：单文件 512 MiB；存储总量 8 GiB（超出返回 507）；
保留期对接现有 `-retention`，随滚动清理一并删除元数据与磁盘实体。

**验证**：`go test ./api/ ./store/` 全绿（覆盖上传-下载闭环、摘要篡改拒绝、越权 403、
文件名穿越收敛、超限 413、nonce 重放、过期查询）；
`python verify/files_check.py` 端到端 **24/24 通过**。

**边界**：中转占用中枢磁盘与带宽，是"够用且客户端零改动"的取舍；
超大文件的高频分发仍应优先走 L1 的 P2P 直传。

## 4. 与对标产品对照：学什么、不学什么

> 本节只作网络/交付形态层的对照。**拆包后的完整功能面、授权模型、编排面（中枢侧 MCP）、
> 数据模型与分优先级的吸收清单，见 `docs/benchmark-huizhi-mesh-lessons.md`（2026-09-29 新增）。**

| 维度 | 对标产品 | 改造后方案 B | 结论 |
|---|---|---|---|
| 网络前提 | 要求"同局域网或已打通"（推给客户） | L0 直接可用；L1 给一页纸放行；L2 才用隧道 | **比它多走一步**：跨 VLAN 我们给标准与工具 |
| 外部依赖 | 无 | L0 / L1 无；仅 L2 需 VPS | 对齐 |
| 数据位置 | 客户内网 | 客户内网（厂区） | 对齐 |
| 安装 | 邀请码 + 一行命令 | §3.4 实现 | 对齐 |
| 升级 | 手工（下载 → 备份 → 执行） | 可做自检 + 一键升级（后续） | **可超车点** |

**不学的**：把跨网问题**完全**推给客户。
目标是"能不问就不问"——L0 / L1 客户近乎零配置可用，L2 给现成隧道方案。

## 6. 验收用例（T10，厂区内网）

- **T10-a（L0）**：同网段两机，mDNS P2P 传文件成功（现有能力回归）
- **T10-b（L1 控制面）**：跨 VLAN 客户端心跳上线、任务闭环（走服务端）
- **T10-c（L1 P2P）**：跨 VLAN 经服务端 peer 目录直连传文件成功
- **T10-d（L1 负例）**：`p2p_allow` 白名单外的节点仍被拒（改造未破坏安全边界）
- **T10-e（L2 控制面）**：无内部线路时经 frp 隧道心跳上线 + 任务闭环
- **T10-f（L2 文件）**：跨端文件经**服务端中转**可用（依赖 §3.5，**已实现**）。
  自动化回归见 `verify/files_check.py`（24/24）；多机实测补充"两台真机互投"即可。
- **T10-g（任务产出物取回）**：执行机把任务产出物经 `mesh.relayfile` 上传后，
  控制台 `/console/api/files` 能列出并直接下载 —— 这是"产出物留在执行机"的根治项。
