# 自助入网：邀请码 + 一键安装 + 自检回传

> 状态：**已实现并端到端验证通过**（2026-09-29）
> 相关代码：`agent-mesh-server/store/invites.go`、`api/invite.go`、`api/ratelimit.go`、
> `web/join.html`、`web/install-client.*.tmpl`、`agent-mesh-client/core/enroll.go`、
> `agent-mesh-client/service_other.go`
> 端到端验证：`python verify/enroll_check.py`

## 1. 它解决什么问题

改造前，给一台电脑接入要这么做：

1. 把客户端程序拷过去（U 盘 / 微信）；
2. 手工打开 `agent-mesh.json`，填服务端地址、集群密钥、CA 路径；
3. 在管理员终端里执行 `client.exe install`；
4. 打电话问对方"控制台上看到你的机器了吗"，看不到就远程连过去看日志。

**十几个人的公司 = 十几次这样的工序。** 这一层把整段工序换成：

> 管理员点一下「签发邀请」→ 把一段命令发给对方 → 对方粘进管理员终端 → 完成。

现场没有第二通电话：装完的结果会自动出现在控制台的「入网记录」里。

## 2. 全流程

```
管理员（控制台）                     员工机器（目标电脑）
─────────────────                   ────────────────────────
签发邀请码
  ↓ 得到一行命令 + 落地页链接
                ──── 对方粘贴执行 ────→
                                    install.ps1 / install.sh
                                      ↓ （极薄：只负责下载程序）
                                    下载客户端（中枢自带分发）
                                      ↓
                                    client enroll
                                      1. 取配置包（邀请码 → 地址+密钥+CA）
                                      2. 写 ca.pem 与 agent-mesh.json
                                      3. 复制程序到安装目录
                                      4. 注册并启动开机自启服务
                                      5. 打一次签名心跳（验网络/密钥/证书）
                                      6. 轮询设备列表（验服务真的在跑）
                                      7. 回传自检结果
  ←──── 控制台「入网记录」可见 ────
```

## 3. 服务端

### 3.1 启动参数（新增两项）

| 参数 | 环境变量 | 说明 |
|---|---|---|
| `-client-pack` | `AGENT_MESH_CLIENT_PACK` | 客户端二进制所在目录，供 `/join/<码>/client` 分发。**留空则该端点 503**，落地页会给出放置指引 |
| `-public-url` | `AGENT_MESH_PUBLIC_URL` | 邀请页与脚本里对外声明的基址。走反向代理/隧道时必填；内网直连可留空（按请求 Host 推导） |

客户端目录的文件命名（按优先级）：

```
client-windows-amd64.exe   ← 推荐
mesh-client.exe / client.exe / agent-mesh-client.exe

client-linux-amd64         ← 推荐
mesh-client-linux-amd64 / agent-mesh-client / client
```

都找不到时会退化为「文件名含 windows / linux 的任意文件」，避免因为漏打后缀而卡住。

编译放置示例：

```bash
go build -o bin/agent-mesh-client.exe ./agent-mesh-client   # Windows
GOOS=linux go build -o bin/agent-mesh-client ./agent-mesh-client  # Linux
# 然后放进 -client-pack 指定的目录
```

### 3.2 控制台

「接入与设备 · 签发邀请」面板：

- **备注**：工位 / 姓名 / 资产号，用于日后对账
- **有效期（分钟）**：默认 30，上限 7 天
- **使用次数**：`仅用 1 次（一码一机）` 或 `不限次数（同批多台）`

签发后会**一次性**显示：明文邀请码、Windows / Linux 两条命令、落地页链接。
**明文码之后再也查不到**——库里只存 SHA-256 哈希，控制台被翻遍也翻不出可用凭证。

另外两个面板：

- **邀请记录**：编号（哈希前缀）、备注、状态、用量、有效期倒计时、最近使用者、作废按钮
- **入网记录**：节点、系统、IP、成功/失败、**逐条自检明细** —— 这是"装没装好"的唯一权威答案

## 4. 客户端

```bash
# 由服务端下发的脚本自动调用（推荐，码走 stdin，不出现在命令行里）
agent-mesh-client enroll --server http://10.0.0.5:8080 --code-stdin

# 手工调用
agent-mesh-client enroll \
  --server http://10.0.0.5:8080 \
  --code ABCD-EFGH-IJKL-MNOP \
  --install-dir /opt/agent-mesh/client \
  --data-dir /var/lib/agent-mesh
```

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--server` | 必填 | 中枢地址，可省协议（自动补 `http://`） |
| `--code` / `--code-stdin` | 必填 | 邀请码。**推荐 stdin**：Linux 上 `/proc/*/cmdline` 对同机其他用户可读 |
| `--id` | 主机名 | 节点标识，须与控制台里期望看到的名字一致 |
| `--install-dir` | Win: `C:\Program Files\AgentMesh\Client`<br>Linux: `/opt/agent-mesh/client` | 程序与配置的落地位置 |
| `--data-dir` | Win: `%ProgramData%\AgentMesh`<br>Linux: `/var/lib/agent-mesh` | 日志与下载 |
| `--p2p-port` | 6001 | `0` 表示关闭 P2P |
| `--no-service` | 关 | 只写配置，不注册系统服务（排障用） |
| `--timeout` | 3m | 整体超时 |

其它子命令：`install` / `uninstall` / `status`。

### 4.1 Linux 上真的装了自启（不再是空壳）

原实现里非 Windows 平台的 `installService` 一律返回错误，后果是 Linux 上只能前台跑，
一关终端就断心跳 —— 这正是对标产品在安装页上用加粗警告提醒用户的那件事。

现在补齐了 systemd：

- `installServiceAt(exePath)`：写 `/etc/systemd/system/agent-mesh-client.service`，
  `Restart=always`、`WantedBy=multi-user.target`，然后 `enable --now`
- `stopService` / `restartService` / `serviceStatus` / `uninstallService`
- 没有 systemd 的环境（容器、Alpine、老发行版）**明确报错并给前台运行指引**，
  不做"静默降级成不生效"——那种问题现场极难排查

## 6. 安全模型与边界

### 6.1 做了什么

| 措施 | 原因 |
|---|---|
| **只存 SHA-256 哈希** | 数据库被拖走也拿不到可用凭证。明文只在签发那一刻出现一次 |
| **CSPRNG 生成**，字符集剔除 `0/O/1/I/L` | 邀请码能换集群密钥，可预测的随机数等于送密钥；剔除易混字符是给现场抄码的人减负 |
| **默认 30 分钟有效期** | 缩短"码在有效期内被猜中"的窗口 |
| **按 IP 固定窗口限流**（`/join` 全组 60/分钟） | 16 位码是可以暴力枚举的，没有限流内网里跑个脚本就能试出来 |
| **限流键只取连接地址，不信任 `X-Forwarded-For`** | 否则攻击者填一个头就能把配额刷成无限 |
| **处理 `X-Forwarded-Proto` 只在未显式配置 `-public-url` 时** | 显式配置永远优先，反代场景不会算出错误协议 |
| **邀请码走 stdin 传给客户端** | Linux 上命令行参数对同机其他用户可见 |
| **落盘随机化 + 只存哈希 + 作废即失效** | 邀请码不是长期凭证 |
| **`Cache-Control: no-store`** | 配置包带密钥，任何中间层都不许缓存 |

### 6.2 明确的边界（**别误解成强席位控制**）

我们的鉴权是**集群共享密钥**。邀请码负责"安全地把密钥送到机器上"，
并留下"谁在什么时候接入"的审计线索；`max_uses` 约束的是**换取配置包这个动作**的次数。

因此：

- 一旦机器拿到密钥，它就是集群的一员，服务端不会因为"名额超了"把它踢掉；
- 两台机器同时抢一枚一码一机：两台都能取到配置（极短窗口），
  但**第二台的 `/report` 会因名额已尽而被拒**，控制台的入网记录里会留下这条失败 —— 这是刻意保留的可见性；
- **真正的强席位控制需要改成按设备签发独立密钥**，属于后续工作项（见 §8）。

这是当前"不改鉴权协议、零破坏风险"取舍下的必然结果，写在这里以免被当成缺陷。

### 6.3 TOFU（首次信任）

取配置包这一刻，客户端手上还没有服务端 CA，**只能跳过证书校验**（HTTPS 部署时）。
拿到 `tls_ca_pem` 后立刻固定下来，之后所有通信（含常驻服务自己）都走严格校验。

替代方案是"先把 ca.pem 拷到每台机器"——那正是本流程要消灭的工序。
对标产品默认就是 HTTP + 自签，连这一步都没有；我们在 HTTP 场景下完全等价，
在 HTTPS 场景下给出了显式分支与固定 CA。

## 7. 排障对照表

| 现场现象 | 原因 | 处理 |
|---|---|---|
| 客户端提示"需要管理员/root 权限" | 没用提权终端 | **不会消耗邀请码**，换提权终端重跑同一条命令即可 |
| 提示"邀请码已过期" | 默认只有 30 分钟 | 管理员重新签发；批量场景把有效期调长 |
| 提示"次数已用尽" | 默认一码一机 | 重新签发，或签发"不限次数" |
| 提示"连不上中枢" | 地址/端口/网络 | 在目标机上 `curl <中枢>/healthz` 验证可达 |
| 自检"心跳连通性"失败 | 密钥不符，或双方时间偏差 > 5 分钟 | 核对时间同步；重新签发（码里有最新密钥） |
| 自检"控制台可见"失败 | 常驻服务没起来 | 看 `--data-dir/logs` 下的日志；`client status` 查服务状态 |
| 命令执行后 503 | 中枢没配 `-client-pack` | 编译客户端并放进该目录，落地页会提示 |
| 覆盖安装目录里的程序失败 | 旧版服务还在运行 | 先 `client uninstall`，再重跑接入命令 |
| 落地页显示"无效" | 码不存在/被清理 | 重新签发 |
| 旧版本还在跑、新版本装不上（`Copy-Item` 报被占用） | 安装必须先停服，脚本已处理 | 见 §10：直接重跑脚本，不必先卸载 |
| 换路径重装后重启起来的是旧版 | 服务注册项没跟着改指 | 见 §10：默认已接管；装完看最后的「注册项校验」 |
| 重装后所有老节点掉线 | 重装时换了新密钥/证书 | 见 §10：默认沿用旧密钥与旧证书；换过就重新入网 |
| 对方机器提示"连不上中枢" | 中间隔着 NAT，反向不通 | 见 §11：保证**对方能主动访问**中枢地址即可 |
| 客户机执行命令报"连接被拒绝"，但网络其实是通的 | 命令里的地址是 `127.0.0.1`（从开发机打开页面时算出来的） | 见 §12：把**内网地址的链接**发给客户，让他自己打开页面取命令 |

## 10. 重装、升级与「换路径安装」

### 10.1 为什么这是个坑

Windows 的**服务名全局唯一**。旧版装在 `A` 目录、这次装到 `B` 目录，注册表里那条
（`AgentMeshServer` / `AgentMeshClient`）仍旧指向 `A\server.exe`：

- 安装全程看着成功——新文件确实拷到 `B` 了；
- 重启后 SCM 先把 `A` 拉起来，新装的这份永远轮不到开机自启；
- 于是两个实例抢同一个端口/同一个节点身份，而这份混乱只在重启后才会暴露。

所以 PowerShell 脚本与 `install` 子命令都对这种情况做了**接管**，顺序是硬约束：

```
停止旧实例（等进程真正退出，文件句柄才会释放）
   ↓
注销旧注册项（不等到注册项消失就重建，会撞 1078 ERROR_SERVICE_EXISTS）
   ↓
用当前路径 CreateService 并启动（旧目录的文件保留，不删）
```

Go 侧同样处理——手工执行 `server.exe install` / `client.exe enroll` 时也能接管。
对照产品的普遍做法是报错让你先卸载，我们把这一步省掉了：**服务名是本产品专属，
指向别路径几乎必然是旧版本遗留**，要求人回去卸载只是在复现我们要消灭的工序。

### 10.2 凭据与证书一律沿用

重装最容易把事情搞大的地方是「顺手重新生成」：

| 重新生成了什么 | 后果 |
|---|---|
| 集群密钥 | **所有已接入节点一次性鉴权失败**，全部掉线 |
| TLS 证书 | 所有客户端的 `ca.pem` 校验失败，必须重新入网拿新 CA |
| 节点 ID | 控制台多出一堆同名不同 ID 的幽灵设备 |

所以脚本默认从旧配置里沿用 `secret` / `console_user` / `console_pass` / `public_url` /
`client_pack`（客户端还会沿用 `id` 与 `tls_ca`），并打印一行：

```
[沿用] 已复用既有集群密钥与控制台口令 —— 已接入的节点不会掉线
```

确实要换时显式传参覆盖即可；TLS 要重签加 `-RegenCert`。

> 顺带说明：这也意味着**不用管 uninstall**。`install-server.ps1` 可以直接反复跑，
> 换端口、换目录、升版本都是同一条命令，而且不需要先把旧的卸掉。

### 10.3 装完唯一的权威判据

健康自检只能证明"现在有人在 8099 上响应"，证明不了响应的是这次装的这个程序。
脚本最后一步因此去看注册项：

```
[校验] 自启动注册项指向本次安装的程序：C:\Program Files\AgentMesh\Server\server.exe
```

这一行通过，才谈得上"重启后没跑成旧的"。指向别处时会直接给出处理命令
（`sc.exe delete <服务名>` 后重跑脚本）。

### 10.4 保留旧行为的开关

确实存在"同一台机器上要同时维护两套实例"的场合（比如灰度验证新版），此时：

```powershell
.\install-server.ps1 -KeepLegacyService ...      # 检测到路径不同就报错退出
client.exe install --no-takeover                  # 子命令侧的同义开关
```

## 11. 跨网段 / 二级路由（NAT）下给对方装客户端

### 11.1 先想清楚方向

客户端是**主动方**：它拨中枢、做签名心跳、拉任务。所以链路要求只有一条：

> **对方机器能主动访问到中枢的那个 `ip:port`。反方向通不通无所谓。**

典型拓扑「光猫 → 路由器 → 开发机」里，光猫侧（`192.168.1.x`）根本没法主动访问
路由器内侧（`192.168.2.x`），因为中间那层做了 NAT —— 这正是同事电脑 `192.168.1.3`
连不上 `192.168.2.131:8099` 的原因。它**不是软件的 bug**，是网络拓扑。

排查一句话：在对方机器上执行这条，通了就一定能装：

```powershell
Test-NetConnection 192.168.2.131 -Port 8099
```

### 11.2 三种解法（按推荐度）

| 方案 | 做法 | 适用 |
|---|---|---|
| **① 物理挪到同一网段** | 把对方电脑接到路由器 LAN 口或 WiFi，让它拿到 `192.168.2.x` | 有网线/WiFi 时首选，零配置、还能用 mDNS 自动发现 |
| **② 路由器端口映射** | 管理页 → 转发规则/虚拟服务器：外网口 8099 → 内部 `192.168.2.131:8099`（TCP）。对方访问 `http://<路由器WAN口IP>:8099` | 对方机器搬不动时 |
| **③ 把中枢挪到上级网段** | 开发机接光猫 LAN/WiFi，拿到 `192.168.1.x` | 只临时验证时；会让内网其他设备访问不到它 |

走 ② 时有三个参数必须跟着改，否则装机命令里写的仍是那个连不上的内网地址：

```powershell
.\install-server.ps1 -Addr ":8099" `
  -PublicUrl  "http://<路由器WAN口IP>:8099" `
  -ClientPack "C:\Program Files\AgentMesh\Pack" `
  -TLS -CertHost <路由器WAN口IP>
```

- `-PublicUrl`：写进落地页与安装脚本。不配的话按请求 Host 推导，跨网段时推出来的是错地址；
- `-ClientPack`：放 `client-windows-amd64.exe` 的目录，对方靠它下载客户端；不配则 503；
- `-CertHost`：开了 TLS 时，把对方实际访问的地址写进证书 SAN，否则握手失败。

这三个参数会被写进 `agent-mesh.json`，之后重装会自动沿用，不用每次都敲。

### 11.3 建议的顺序：先在开发机自测一遍客户端

别一上来就拿同事电脑试——那样同时引入了"服务端配置"和"跨网段连通性"两个变量，
出了分不清是哪边的问题。先在**开发机本机**装一个客户端（它既是服务端又是节点）：

```powershell
cd D:\guli\projects\agent-mesh\deploy
.\install-client.ps1 -ServerURL "http://127.0.0.1:8099" `
                     -Secret "C:\Program Files\AgentMesh\Server\agent-mesh.json 里的 secret"
```

控制台里出现这台机器、日志无连接报错，说明服务端一侧没问题。
**此后再让对方机器装，剩下的变量就只有网络**。

也可以两条腿都试：`Test-NetConnection` 通了以后，控制台签发邀请、把一行动令发给对方，
对方在管理员终端里粘贴执行即可（见上文 §2 全流程）。

### 11.4 `Test-NetConnection` 不通时，按这个顺序查

| # | 检查 | 命令 / 判据 |
|---|---|---|
| 1 | 双方是否真的同网段 | 对方机器上 `ipconfig`：笔记本同时连着 WiFi 和网线时，路由表可能走另一条路 |
| 2 | 中枢到底有没有在听 | 中枢本机：`Get-NetTCPConnection -LocalPort 8099 -State Listen` 要有一行 LISTENING |
| 3 | 换端口后防火墙是否重建过 | 规则是按端口建的，改了端口必须重跑安装脚本（它会自动删旧规则、建新的） |
| 4 | 端口映射是否生效 | 路由器管理页确认规则，并在对方机器 Telnet `Test-NetConnection <WAN口IP> -Port 8099` |
| 5 | 对方是否开了代理软件 | clash-verge 这类会把请求送去 `127.0.0.1:7890`。客户端读的是 `HTTP_PROXY`/`HTTPS_PROXY` **环境变量**，对方终端里执行 `echo $env:HTTPS_PROXY`；有的话临时 `$env:HTTPS_PROXY=""` 再跑接入命令 |

第 5 项最容易冤枉人：代理劫持下表现为"NAT 没配好"的所有症状，但网络其实完全通。

### 11.5 不要 /join 端点也能装（手工装机）

对方连不上中枢是装不了；中枢还没配 `-ClientPack` 时，走 `deploy/install-client.ps1` 手工装同样有效——
把脚本与 `client.exe` 一起递过去（U 盘 / 局域网共享 / 微信均可）：

```powershell
.\install-client.ps1 -ServerURL "http://<对方能访问的中枢地址>:8099" -Secret "<集群密钥>"
```

这条路径不需要 `-ClientPack`，也不需要邀请码；代价是拿不到控制台里的「入网记录」自检明细，
结果只能看 `install-client.ps1` 自身的自检输出与客户机日志。

## 12. 邀请页里的地址是从哪来的（`127.0.0.1` 陷阱）

### 12.1 一句话原理

> 落地页与安装脚本里的地址，**按「你打开这个页面的地址」拼**。
>
> - 没配 `-public-url` 时：用请求里的 `Host`；
> - 配了 `-public-url`：一律用它，与怎么打开无关。

所以「在开发机上用 `http://127.0.0.1:4024/join/<码>` 打开，再把页面上那行命令发给客户机」
**必然失败**——那台机器执行时 `127.0.0.1` 指的是它自己，报错是「连接被拒绝」，
看起来像网络不通，其实是地址拿错了。这个坑现在页面上会直接警告（见 12.3）。

### 12.2 客户机该怎么做（三种做法，按省事程度）

| # | 做法 | 操作 | 适合 |
|---|---|---|---|
| **① 发链接，不发命令**（推荐） | 把 `http://<中枢内网IP>:<端口>/join/<码>` 发给客户，**让客户在自己机器上用浏览器打开**，页面会自动生成对客户有效的命令，他复制执行即可 | 常规装机；中枢地址稳定 |
| **② 固定基址** | 启动时加 `-public-url http://<中枢内网IP>:<端口>`（或 `install-server.ps1 -PublicUrl ...`），此后你在任何机器、用任何地址打开，页面给出的命令都固定正确 | 要批量装很多台；地址已确定不再变 |
| **③ 手工装机** | 走 §11.5：把 `install-client.ps1` + `client.exe` 递过去，`-ServerURL` 手填客户能访问的地址 | 客户机上不了 `/join` 端点（无 `-ClientPack`、或跨 NAT 不通） |

做法 ① 的要害是**让客户自己打开链接**：命令是服务端按请求 Host 现算的，
只有客户用自己那条路打开，算出来的地址才对。你替他复制命令等于替他用了你的地址。

### 12.3 页面上现在会怎么提示

从回环地址（`127.0.0.1` / `localhost` / `::1` / `0.0.0.0`）打开落地页时，页面顶部会出现红色警告块：

- 说明该地址只在中枢本机有效；
- 列出**本机探测到的每个内网 IPv4，并标注来源网卡**，每条都带复制按钮；
- 给出上述做法 ① / ② 的指引。

**控制台签发时同样会提醒**：在回环地址下签发邀请码，结果区会插一段红色警示，
并把可转发的内网链接直接列出来。这一处比落地页更要紧 ——
管理员通常是在控制台签完码、复制链接就转发出去，**根本不会打开落地页**。

配套的两处改动：

- **启动日志**会把客户机该用的地址打出来（并提示「未配置 -public-url」）：

  ```
  [入网] 未配置 -public-url：邀请页给的地址跟着「打开页面的地址」走。
           客户机器请从下面任一地址打开邀请页（控制台也挂在其下）：
             http://192.168.2.131:4024/join/<邀请码>   [以太网]
             http://172.28.160.1:4024/join/<邀请码>   [vEthernet (Default Switch)]  <- 虚拟网卡，客户机大概率访问不到
           若希望固定不变，请加 -public-url http://<上面的地址>。
  ```

- **地址枚举与排序**（`internal/netutil.LocalAddrs`）：

  | 规则 | 说明 |
  |---|---|
  | 过滤 | 回环、未指定（0.0.0.0）、链路本地（169.254/16）、组播；跳过 down 的网卡 |
  | ① 真实网卡优先 | 疑似虚拟/隧道网卡（WSL、VMware、VirtualBox、Hyper-V、Docker、Tailscale、ZeroTier、TAP/TUN…）**靠后并标注** |
  | ② 同组内私网优先 | 10. / 172.16-31. / 192.168. 排在前 —— 厂区内网要的就是它们 |
  | ③ 按 IP 数值升序 | 保证输出稳定（避免字符串比较把 `10.0.0.9` 排到 `10.0.0.10` 之后） |

  虚拟网卡**不剔除只降级**：真实网卡全都不在时，它仍是唯一线索。
  这一条是现场踩出来的 —— 开发机同时有「以太网 192.168.2.131」和
  「vEthernet (Default Switch) 172.28.160.1」，按字符串排序时虚拟网卡的
  `172.*` 反而排在前面，管理员照第一条发链接就必然连不上。

  > 故意不把 `br-*` 当虚拟网卡：OpenWrt 上的 `br-lan` 就是真实业务网卡。

### 12.4 前提（否则做法 ① 也白搭）

1. 客户机与中枢**网络可达**（同网段，或已按 §11 打通），用 `Test-NetConnection <中枢IP> -Port <端口>` 验；
2. 中枢机器**放行了该端口**（安装脚本会自动建防火墙规则，换端口要重跑）；
3. 中枢配了 `-client-pack`，否则页面上会出现「客户端安装包尚未就绪」，命令跑了也拿不到客户端。
