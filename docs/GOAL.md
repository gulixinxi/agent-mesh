## 3. 必须提前说清的两条边界（做不到，不是工时问题）

1. **不能实时阻断。**
   对标产品的"防泄密"本质也是 `redact` 脱敏 + 审计可见性形成威慑，**不是实时拦下来**。
   若客户要的是「员工往 AI 里粘贴身份证号时当场被拦」，那是另一款产品（需要端侧驱动/过滤代理），当前架构做不到。

2. **加密库的对话采集做不到。**
   实测 Trae CN 的会话主库 `ModularData\ai-agent\database.db`（12.5 MB）
   熵 **8.00/8.00**、无 SQLite 明文；`config.db` / `env_codekg.db` 同样加密。
   仅 `state.vscdb` 是明文，但**只有草稿与模型列表，没有对话正文**。
   → IDE 类客户端只能做**存在性检测**（知道装了），做不了对话采集。
   → 旁证：汇智中枢支持的执行器枚举里也**不含 Trae**。

### G-1 结论摘要（改变了后面所有目标的地基）

> ⚠️ **结论的适用边界（2026-10-01 修正）**
> 下面的否定结论**只对豆包成立**。曾经据此外推出「本地没有可读对话正文、对话采集做不了」——
> 这个外推是错的。同一次普查里 Codex CLI / Cursor / Windsurf / VS Code **全部明文可读**，
> 且 Codex 直接带 token 用量。**单个客户端的结论不能外推到整条产品线**，见 §8。

豆包桌面端把会话存在 **Chromium IndexedDB（LevelDB + SSV 编码）**，而不是 SQLite；
本地能取到的是**会话元数据**（`conversation_id` / `sessionId` / `bot_id` / `querySendTimestamp` / `last_message_index`），
**取不到提问与回答正文，也取不到 token 用量**。

证据是全量字节扫描，不是推理：`chrome_doubao-chat_0` 全部 931 条记录中
**零条**含中文正文；`%LOCALAPPDATA%\Doubao` 与 `%APPDATA%\Doubao` 全目录扫描，
命中的只有 Python/Node 沙箱运行时的 dll/pyd 二进制。

因此 `adapters/doubao.go:97` 那条 SQL（`SELECT ... FROM messages`）在任何版本豆包上都不成立。

顺带验证：ChatGPT 网页版在浏览器侧也不可行——Edge 里 `https_chatgpt.com_0` 的
IndexedDB 存的是 **ECDSA P-256 私钥**（端到端加密密钥库），正文不以可读形式落盘。

## 8. 可读性普查结果（2026-10-01 本机实测）

工具：`tools/probe_readability.py`（可在任意机器上重跑，输出「谁可读 / 谁加密 / 什么粒度」）。
判定口径：**可读** = 取到自然语言正文；**仅元数据** = 只有会话 id/时间戳；**加密** = 熵 > 7.5 或打不开。

| 客户端 | 数据源 | 判定 | 依据 |
|---|---|---|---|
| **Codex CLI** | `~/.codex/sessions/**/*.jsonl`、`archived_sessions/*.jsonl` | ✅ 可读 | 336 个文件，明文 JSONL，含 role/content 正文；**字段含 `input_tokens` / `output_tokens` / `cached_input_tokens` / `total_tokens`** |
| **Cursor** | `%APPDATA%\Cursor\User\globalStorage\state.vscdb` | ✅ 可读 | 明文 SQLite 597 MB，`cursorDiskKV` 表 68,421 行；抽样 703 条中 **232 条含自然语言正文**（`bubbleId:*` 21,009 条、`composerData:*` 230 条） |
| **Windsurf** | `%APPDATA%\Windsurf\User\...\state.vscdb` | ✅ 可读 | 同上结构，抽样 85 条中 6 条含正文 |
| **VS Code** | `%APPDATA%\Code\User\...\state.vscdb` | ✅ 可读 | 同上结构 |
| **豆包 Doubao** | `User Data\Default\.doubao\agent_mode\workspace` | ⚠️ **存疑** | 脚本命中几个几十 KB 的 JSONL，但**不是主对话库**。G-1 的全量字节扫描结论仍然成立：主库 IndexedDB 931 条记录零正文。**不要据这条推翻 G-1** |
| **ChatAA** | `database/llmfarm.sqlite` | 仅元数据 | 抽到表但未命中正文 |

### 三条推论

1. **对话采集 + 日报这条产品线成立**，不需要改架构、不需要网关解密。G-3 的受阻原因不是"没有数据源"，是**我们选错了目标（豆包）**。
2. **对标产品为什么把 `codex` 排在支持的执行器第一位**——那就是它的采集源。它同样采不到豆包，但它采 Codex / Cursor 这类。
3. **错位对我们有利**：明文落盘的恰好是程序员用的 AI IDE（会被喂进公司代码、客户资料、财务数据，最该审计）；通用聊天类（豆包、ChatGPT 网页版）反而加密，而那部分风险本来就低。

### 采集目标优先级

1. **Codex CLI** —— 结构最规整（JSONL）、带 token 用量，是日报的天然数据源，先做它
2. **Cursor / Windsurf / VS Code** —— 同一套 `state.vscdb` KV 结构，写一个解析器三家通吃
3. 其余走 §8 的普查脚本持续扩充

### 边界与合规

- 采集员工对话涉及个人信息，**上线前必须有告知 + 脱敏**。`core/redact.go`（G-2）已经是上报唯一出口的强制关口，正好配套。
- 对标产品也是**强制脱敏、脱敏后为空的条目直接丢弃**——它卖的从来不是"看员工原文"，是"AI 使用能见度 + 防泄密审计"。这个定位要写进对外话术。

## 9. 审计对象的三个存储位置（决定"能不能查"的是位置，不是意愿）

推论链「AI 需要长期记忆 → 必然要存储 → 因此一定可被审计」**方向正确但需拆分**：
「必然被存储」成立，「我们能不能查」取决于**它存在哪**。实测三类：

| 存储位置 | 实例 | 可审计性 | 我们的做法 |
|---|---|---|---|
| **本地明文** | Codex 会话 JSONL、Cursor/Windsurf/VS Code `state.vscdb`、以及 **AGENTS.md / CLAUDE.md / MEMORY.md / .cursorrules** | ✅ 正文与 token 直读 | 客户端直接解析上报 |
| **本地加密/编码** | 豆包 IndexedDB（SSV 编码）、Trae CN 加密会话库 | ⚠️ 只有会话 id / 时间戳 | 只做存在性与活跃度 |
| **厂商云端** | 豆包、WorkBuddy 的会话——**本地磁盘上根本没有会话库**（实测 `Roaming\WorkBuddy` 与 `Local\WorkBuddy` 无任何 db/json/jsonl） | ❌ 本地取不到 | 需厂商企业 API 或管理后台，长期项 |

### 「记忆文件」是被忽略的一层，且优先级应最高

实测本机明文记忆/规则文件：`~/.workbuddy/MEMORY.md`（7.4 KB）、`~/.codex/AGENTS.md`（5.7 KB），
以及多个项目根下的 `AGENTS.md` / `CLAUDE.md`。它们的特点：

1. **业务浓度高于对话**——写的是项目背景、技术栈、业务规则、客户名，不是闲聊；
2. **采集成本最低**——扫描 md 文件即可，无需解析 SQLite 或 LevelDB；
3. **合规阻力最小**——不碰对话隐私，属于"公司设备上的公司文件"；
4. **它本身就是最大的外泄面**——写进记忆文件、再用云端 AI，内容就随请求离开设备。
   「AI 需要长期记忆」这个事实本身，就意味着公司信息正在往外走。

→ 对外话术可 hardening 为一句更硬的：
**「你们公司有多少业务上下文，已经被写进 AI 的记忆里、存在别人的服务器上。」**
