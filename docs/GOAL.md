## 3. 必须提前说清的两条边界（做不到，不是工时问题）

1. **不能实时阻断。**
   对标产品的"防泄密"本质也是 `redact` 脱敏 + 审计可见性形成威慑，**不是实时拦下来**。
   若客户要的是「员工往 AI 里粘贴身份证号时当场被拦」，那是另一款产品（需要端侧驱动/过滤代理），当前架构做不到。

2. **加密库的对话采集做不到。**
   实测 Trae CN 的会话主库 `ModularData\ai-agent\database.db`（12.5 MB）
   熵 **8.00/8.00**、无 SQLite 明文；`config.db` / `env_codekg.db` 同样加密。
   仅 `state.vscdb` 是明文，但**只有草稿与模型列表，没有对话正文**。
   → IDE 类客户端只能做**存在性检测**（知道装了），做不了对话采集。
   → 旁证：汇智中枢支持的执行器枚举里也**不含 Trae**。

### G-1 结论摘要（改变了后面所有目标的地基）

豆包桌面端把会话存在 **Chromium IndexedDB（LevelDB + SSV 编码）**，而不是 SQLite；
本地能取到的是**会话元数据**（`conversation_id` / `sessionId` / `bot_id` / `querySendTimestamp` / `last_message_index`），
**取不到提问与回答正文，也取不到 token 用量**。

证据是全量字节扫描，不是推理：`chrome_doubao-chat_0` 全部 931 条记录中
**零条**含中文正文；`%LOCALAPPDATA%\Doubao` 与 `%APPDATA%\Doubao` 全目录扫描，
命中的只有 Python/Node 沙箱运行时的 dll/pyd 二进制。

因此 `adapters/doubao.go:97` 那条 SQL（`SELECT ... FROM messages`）在任何版本豆包上都不成立。

顺带验证：ChatGPT 网页版在浏览器侧也不可行——Edge 里 `https_chatgpt.com_0` 的
IndexedDB 存的是 **ECDSA P-256 私钥**（端到端加密密钥库），正文不以可读形式落盘。

## 5. 建议顺序与理由

```
G-2（脱敏，无依赖可先做）
 └→ G-1（验证真实 schema，拿到真机后）
      └→ G-3（用量/日报）
G-4（存在性探测，独立）
G-6 → G-5（治理层）
```

**理由**：G-2 零依赖、且是目前最大的合规风险（对话原文裸奔进数据库），应该第一个开工。
G-1 卡在「需要真实豆包机器」这一外部条件上，先排上日程、拿到机器立刻做。

**不推荐的顺序**：先扩适配器（多接几个 AI 客户端）。
理由是 G1 的覆盖面再广，只要**底座的 schema 没验证、脱敏没做**，接到的数据也不可信。

## 7. G-1 关后的岔路口：先选数据源，再谈 G-3/G-4

G-1 的结论把「对话正文」这条路掐断了，但**产品要不要继续、往哪走，取决于你选哪条**：

| 路径 | 能拿到什么 | 代价 | 适合 |
|---|---|---|---|
| **① 改做「AI 使用行为台账」** | 会话创建时间、会话 ID、bot、消息序号 → 活跃度与频次 | Go 里实现 LevelDB SSTable 读取 + SSV 解码（工程量中等） | 只想证明「谁在用、用多少」 |
| **② 换目标：找真正把正文落盘的客户端** | 取决于对象，**必须逐个实测** | 先花小成本做一轮「可读性普查」 | 对话日志是刚需（审计的故事要靠它讲） |
| **③ 改架构：网关/代理层采集** | 完整正文 + token | 需要在企业网关做 HTTPS 解密，或客户端 Hook —— **另一款产品** | 客户明确要求「知道员工问了什么」 |

**我的建议**：先花小成本做「路径 ② 的可读性普查」，把本机已装的 AI 客户端
（Cursor / Claude / Kimi / MiniMax / Ollama 等）逐个用本报告同一套方法实测一遍，
形成一张「谁可读、谁加密、读到什么粒度」的表。
这张表比任何估计都值钱——它直接决定 G-1/G-3/G-4 到底是「做」还是「改需求」。
